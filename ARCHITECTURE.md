# Integrated backend architecture

Person 4 FastAPI (`api.main:app`, port 8000) owns mission planning and the public dashboard API. Its LangGraph workflow calls unchanged Person 1 REST (`landing_site_analyzer.app:app`, port 8001), Person 2 REST (`visibility_planner.api:app`, port 8002), and Person 3 REST (`moon_navigation`, port 3003) through `tools/member_adapters.py`. Person 3's clean source is preserved under `original_modules/person3/moon_navigation`. Navigation is called only when required and when `LUNA_NAV_TARGET_LAT`/`LUNA_NAV_TARGET_LON` specify a destination. Person 5 owns the dashboard and is not modified here.

The original supplied modules are preserved in `original_modules/person1` and `original_modules/person2`. Member 1 uses a dynamic south-polar search region (configurable in `.env.example`). Member 2 receives each selected site's coordinates and each requested UTC date/duration. The adapter maps terrain-aware summary fractions into Person 4 hours. It rejects mismatched site, coordinates, frame, or interval. Supplier `REAL` and `PARTIAL` become `UNVERIFIED` in Person 4 until an independent scientific review exists; `MOCK` stays `MOCK`. Thus real-backed integrated requests may return candidates but no final recommendation. No measurement is silently promoted to VERIFIED.

The public API and JSON schema remain Person 4's existing `/health` and `/mission/*` endpoints. Startup script `scripts/start_integrated.ps1` launches the two member services and the public API. For a standalone mock demo, leave `LUNA_SITE_URL`, `LUNA_VISIBILITY_URL`, and `LUNA_NAVIGATION_URL` unset and run only Person 4. Service failures return 502; no silent fallback to mocks occurs when a real URL is configured.
